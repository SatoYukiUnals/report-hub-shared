# 調査・作業計画・実施結果は HTML レポートで出す（report-hub）

調査結果・作業計画・実施結果・レビュー・確認事項は、すべて `<report-hub>/reports/` 配下の HTML として出力する。
report-hub はローカル専用のレポート閲覧・回答サーバーで、ページ内の確認事項にユーザーがその場で回答でき、その回答を AI が読んで作業を続けられる。

チャット本文への箇条書きだけで済ませない（チャットには結論とレポートの URL だけを短く書く）。
MD での報告物は作らない。ローカルの TASK.md / TODO.md / PLAN.md も作らない。
※ ここでいう「成果物」は調査・作業計画・実施結果の**報告物**を指す。リポジトリ内の設計ドキュメント（設計書・テスト仕様書等の md）は従来どおり md で作成する。

出すのは次の 4 つ。

| 成果物 | 中身 |
| :--- | :--- |
| 調査結果 | 影響範囲・原因・現状の調査結果 |
| 作業計画 | 着手前に出して承認を得る。対応内容（箇条書き 3 行程度）／修正内容／懸念点 |
| 実施結果 | 実施した内容／修正内容／確かめた観点／残課題・確認事項 |
| レビュー | 指摘ごとに対応可否を聞く |

「実施結果」の対象は、コード変更・テスト・ビルド・デプロイ・データ投入など**何かを実行して結果が出たものすべて**。
**実行したコマンドのログは載せない。** コマンド列・テストの出力・ビルドログを貼らない。確かめたことは**観点だけ**を箇条書きで並べる。件数・秒数・手順は書かない。

## 置き場所と URL

- `<report-hub>/reports/<プロジェクト>/<YYYY-MM-DD>_<名前>.html`
- プロジェクト名・レポート名に使えるのは半角英数字・`.`・`_`・`-` のみ。日本語・スペースはサーバーが弾く。
- 閲覧 URL は `http://localhost:5180/r/<プロジェクト>/<名前>.html`。一覧は `http://localhost:5180/`。
- **サーバーが止まっていたら自分で起動する**（案内で終わらせない）。レポートを出す前に応答を確かめ、返らなければ起動してから出す。

  ```bash
  curl -s -o /dev/null -w '%{http_code}' --max-time 2 http://localhost:5180/ \
    || (cd <report-hub> && docker compose up -d)
  ```

  起動した後は、実際に開けるようになったかをもう一度確かめる（立ち上がりに数秒かかる）。
  Docker 自体が動いていない・起動に失敗したときは、そこで止めてユーザーへ伝える（勝手に Docker を入れたり設定を変えたりしない）。

## テンプレートから起こす

`<report-hub>/templates/` の雛形を複製して書き換える。**ゼロから HTML を書かない。**

| テンプレート | 用途 |
| :--- | :--- |
| `qa.html` | 質問・確認事項 |
| `review.html` | レビュー（RV）。指摘ごとに対応可否を聞く |
| `survey.html` | 調査結果 |
| `plan.html` | 作業計画（対応内容・修正内容・懸念点） |
| `result.html` | 実施結果 |

## 確認事項の書き方

確認事項は `<div class="qa" data-qa-id="..." data-question="...">` で書く。

- **末尾にまとめない。** 問いの対象になっている項目を `<div class="item">` で囲み、その中に置く（末尾に残すのは全体の可否を聞く 1 問だけ）。
- **送信ボタンは書かない。** `/assets/answers.js` がページ末尾に［回答する］を 1 つだけ差し込み、全設問をまとめて保存する。
- `data-qa-id` は一度出したら変えない（変えると過去の回答と結び付かなくなる）。
- 設問は静的な HTML で書く。JavaScript で組み立てると一覧の未回答件数に数えられない。
- 指摘を受けて直すときは、**同じファイルを上書きして更新する**（新しいレポートを作らない）。

## 回答を待ち受けて、来たら続きを実行する（30 分）

確認事項を含むレポートを出したら、**チャットで待たずに回答を待ち受ける**。回答が入った時点で AI が起こされ、その内容に沿って続きを実行する。

```
Monitor(
  command: "python3 -u <report-hub>/bin/watch-answers.py <プロジェクト> <名前> --interval 2",
  description: "<名前> の回答待ち",
  timeout_ms: 1800000,     # 30 分
  persistent: false
)
```

- 設問 1 件に回答が入るたびに 1 行届く。全問揃うと `[完了]` で終わる。
- **届いた回答に沿ってそのまま続きを実行する。** 全問揃うのを待つ必要はない。
- 30 分で切れたら、待ち受けが終わったことと未回答が残っていることをユーザーに伝える。放置しない。
- 完了へ移したレポートを見るときは `--done` を付ける。

**自動で実行してよい範囲**

- 回答が指示になっているもの（方針の選択、修正の可否、対応する / しない）は、そのまま実行してよい。
- ただし次は回答があっても**もう一度確認を取る**：本番への反映、データの削除・移行、外部への送信、コミット・プッシュ。
- 回答が「差し戻す」「補足だけで選択なし」のときは実行せず、内容を読んでから判断する。

**限界（ユーザーへ伝えること）**

- 待ち受けは**この会話が動いている間だけ**。閉じると止まる。閉じる前に待ち受け中のレポートがあれば伝える。
- 回答は後から入れても消えない。次のセッションの開始時に `.answers.json` を読めば拾える。

## 回答の取得方法（AI 側）

ユーザーがページで回答すると、同じ場所の `<名前>.answers.json` に保存される。

```bash
cat <report-hub>/reports/<プロジェクト>/<名前>.answers.json
curl -s http://localhost:5180/api/answers/<プロジェクト>/<名前>
curl -s http://localhost:5180/api/answers/<プロジェクト>/done/<名前>   # 完了へ移したもの
```

- ファイルが無い＝**まだ一件も回答されていない**。設問より回答が少なければ未回答が残っている。
- 回答が必要な作業は、**回答を読んでから**進める。勝手に既定値で進めない。

## レポートの状態 ＝ 置き場所で表す（進行中 / 完了）

状態は置き場所で決まる。ファイルの中に状態を書かない（二重管理になるため）。

| 状態 | 置き場所 | 意味 |
| :--- | :--- | :--- |
| 進行中 | `reports/<プロジェクト>/` | 回答待ち、または回答を受けて作業中 |
| 完了 | `reports/<プロジェクト>/done/` | 片が付いたもの。一覧では「完了 n 件」に畳まれる |

**完了へ移す条件**（すべて満たしたとき）

1. そのレポートの確認事項に回答が揃っている（未回答 0）。
2. 実施結果なら、完了確認の回答が「完了でよい」になっている。
3. 画面に触る変更なら、**実画面で開いて確認してある**。

```bash
cd <report-hub>/reports/<プロジェクト>
mkdir -p done
mv <名前>.html <名前>.answers.json done/   # HTML と回答は対で移す
mv done/<名前>.* .                          # 差し戻されたら戻す
```

**勝手に完了へ移さない。** 条件を満たしたうえで、ユーザーの確認を得てから移す。

## 画面に触る変更は、実画面で確認するまで完了としない

API やファイルの検証だけで済ませない。ブラウザで開けば即分かる不具合を、そこを見ないまま「確認した」と書かない。
確認できない事情がある（拡張が繋がらない等）なら、**レポートの残課題に明記してユーザーへ確認を依頼する**。黙って完了にしない。

## 修正内容の書き方 ＝ 画面・機能の単位

ファイル名・行番号の羅列にしない。**読む人が触る単位**（画面・機能・運用）で、いまどうなっていて、それをどう変えたかを書く。
表にせず、対象 1 件を 1 枚のカード（`div.change`）にする。

```html
<div class="change">
  <h3>レポート一覧</h3>
  <span class="tag">いま</span>
  <span class="from">レポート名と更新時刻が並ぶだけで、未回答があるか開くまで分からない</span>
  <span class="arrow" aria-hidden="true">↓</span>
  <span class="tag to">こうした</span>
  <span class="to">答え待ちを上に集めた 1 本のリストにし、未回答と経過日数を各行に出す</span>
</div>
```

- ラベルは、これから直す計画なら「いま」「こう直す」、済んだ話なら「いま」「こうした」。
- カード 1 枚 1 事象。実装の話（関数名・行番号・差分）は書かない。
- 直した不具合は「何が起きていたか → 原因 → どう直したか」を 1 行で。

## 確かめたことの書き方 ＝ 観点だけ

`<h2>確かめた観点</h2>` に `<ul class="aspects">` で**何を見たかだけ**を箇条書きにする。
結果の数字・手順・コマンド・テスト出力は書かない。別のエージェントにレビューを出したなら、それも観点の 1 つとして入れる。

## セッション開始時のルール

- 実施中の作業に計画レポートがあれば、対応内容・修正内容・懸念点と `.answers.json` の回答を確認する。
- `http://localhost:5180/` を見て、未回答が残っているレポートがないか確認する。
- 上記をもとに本日の作業内容をユーザーへ報告してから着手する。

## セッション終了時のルール

- 対応内容・修正内容・懸念点を計画レポートに記録（更新）する。
- 実施結果（実施した内容・結果・確認事項）を HTML レポートにまとめる。
- 完了条件を満たしたレポートがあれば、`done/` へ移してよいかをユーザーへ確認する。

## 計画レポートを出した後の運用ルール

- 計画レポートを作成・更新したら、その時点で一旦作業を止める。
- 着手可否の回答が入るまで実装・編集へ進まない。
- **回答は明示の指示として扱う。** 着手可否に「進める」「採用する」が入ったら、そのまま次の作業を始めてよい。
- 「差し戻す」「見送る」「選択なしで補足だけ」のときは進めず、内容を読んでから判断する。
- 戻せない操作（本番反映・データ削除・外部への送信・コミット）は、回答があっても実行前にもう一度確認する。
