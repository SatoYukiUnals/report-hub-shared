# 調査・作業計画・実施結果は HTML レポートで出す（report-hub）

調査結果・作業計画・実施結果・レビュー・確認事項は、すべて `<report-hub>/reports/` 配下の HTML として出力する。
report-hub はローカル専用のレポート閲覧・回答サーバーで、ページ内の確認事項にユーザーがその場で回答でき、その回答を AI が読んで作業を続けられる。

チャット本文への箇条書きだけで済ませない（チャットには結論とレポートの URL だけを短く書く。URL は返答の最後の行に置く）。
MD での報告物は作らない。ローカルの TASK.md / TODO.md / PLAN.md も作らない。
※ ここでいう「成果物」は調査・作業計画・実施結果の**報告物**を指す。リポジトリ内の設計ドキュメント（設計書・テスト仕様書等の md）は従来どおり md で作成する。

出すのは次の 4 つ。

| 成果物 | 中身 |
| :--- | :--- |
| 調査結果 | 影響範囲・原因・現状の調査結果 |
| 作業計画 | 着手前に出して承認を得る。対応内容（箇条書き 3 行程度）／修正内容／懸念点 |
| 実施結果 | 実施した内容／修正内容／確かめた観点／残課題・確認事項 |
| レビュー | 指摘ごとに対応可否を聞く |

「実施結果」の対象は、コード変更・テスト・ビルド・デプロイ・データ投入など**何かを実行して結果が出たものすべて**。
**実行したコマンドのログは載せない。** コマンド列・テストの出力・ビルドログを貼らない。確かめたことは**観点だけ**を箇条書きで並べる。件数・秒数・手順は書かない。

## 置き場所と URL

- `<report-hub>/reports/<プロジェクト>/<YYYY-MM-DD>_<名前>.html`
- プロジェクト名・レポート名に使えるのは半角英数字・`.`・`_`・`-` のみ。日本語・スペースはサーバーが弾く。
- 閲覧 URL は `http://localhost:5180/r/<プロジェクト>/<名前>.html`。一覧は `http://localhost:5180/`。
- 枚を指すときは、URL の末尾に `#s<枚番号>` のアンカーを付ける（例 `…/<名前>.html#s3`）。
- サーバーが止まっていたら `cd <report-hub> && docker compose up -d` を案内する。

## テンプレートから起こす

`<report-hub>/templates/` の雛形を複製して書き換える。**ゼロから HTML を書かない。**

**様式はスライド（`slide.html`）だけ。** どのレポートもこれを複製して起こす。

- 1 枚ずつ送って見せる形で、表紙には結論を 1 文だけ置く（レポート名や件数の見出しにしない）。
- 判断してほしい項目が 2 つ以上あるもの（レビューなど）は**索引型の表紙**にする。題＝何の話か、判定 1 行、項目の一覧を置く。詳しくは `slide.html` の先頭コメント。
- **様式の例外は無い。** 表が何本あろうと、設問が何問あろうとスライドで出す。表が多いなら枚に割り、設問はその論点を説明した枚の中へ 1 問ずつ置く。
- 枚数は合計 **5 枚前後**を目安にする。1 枚 1 件で割った結果として増えるのは構わないが、まず 5 枚で言えないかを先に考える。
- 書き終えたら `python3 <report-hub>/bin/check-reports.py <ファイル>` を通す。
- スライドで出すときも、中身の型は用途に従う。調査結果なら結論と根拠、作業計画なら対応内容・修正内容・懸念点、実施結果なら修正内容・画面・確かめた観点を、それぞれ枚に割って並べる。

| テンプレート | 用途 |
| :--- | :--- |
| `slide.html` | **これだけを使う。** 調査結果・作業計画・実施結果・レビュー・判断・読み物、すべてこれで出す |
| その他（`qa` / `review` / `survey` / `plan` / `result`） | 縦スクロールの旧雛形。過去のレポートを読むために残してあるだけで、新しく起こすときには使わない |

**過去に出したレポートは作り直さない。** 既に出した縦スクロール様式のものはそのまま残す。

## 書き方の決め

- **1 文ごとに改行する。** 1 文を 1 つの `p` か `li` にし、「。」で文を続けない。
- 1 項目・1 セルは 1 行（目安 60 字）。長くなるなら項目を割るか、`details` や付録へ回す。
- **ID は単独で書かず、名前を添える**（例「SC-00-05 受注先への更新メール画面」）。添えるのは各枚の初出だけでよい。
- **項目が 3 つ以上並ぶもの・属性を見比べるものは表にする。** 文章で並べない。
- **括弧の補足と二重否定は書かない。** 言い切りで書く。

## 確認事項の書き方

確認事項は `<div class="qa" data-qa-id="..." data-question="...">` で書く。

- **末尾にまとめない。** 問いの対象になっている項目を `<div class="item">` で囲み、その中に置く（末尾に残すのは全体の可否を聞く 1 問だけ）。
- **送信ボタンは書かない。** `/assets/answers.js` がページ末尾に［回答する］を 1 つだけ差し込み、全設問をまとめて保存する。
- `data-qa-id` は一度出したら変えない（変えると過去の回答と結び付かなくなる）。
- 設問は静的な HTML で書く。JavaScript で組み立てると一覧の未回答件数に数えられない。
- スライド様式でも同じで、設問はその論点を説明した枚の中に置き、末尾の `ask` 枚へ集めない。
- **設問には現物を添える。** 判断の対象が画面・レイアウト・データの並び・処理の流れなら、スクリーンショットか図を同じ枚（`div.item`）の中に置いてから聞く。文章だけで「これでよいか」と聞かない。
  - 画面は `figure.shot`（`img` ＋ 1 行の `figcaption`）、順序・分岐は `<pre class="mermaid">` の図、比較は「いま」→「こうする」の `div.change` にする。
  - まだ作っていない・撮れない事情があるときは、`p.why` に「現物なし」と 1 行書いてから聞く。
- 上書きするのは、同じ問いのまま直すときだけ（誤字・事実誤り・設問の言い回し）。回答を受けて次の判断が要るなら、新しいレポートを起こす（下記「1 レポート ＝ 1 回の問いかけ」）。

## 回答を待ち受けて、来たら続きを実行する（30 分）

確認事項を含むレポートを出したら、**チャットで待たずに回答を待ち受ける**。回答が入った時点で AI が起こされ、その内容に沿って続きを実行する。

```
Monitor(
  command: "python3 -u <report-hub>/bin/watch-answers.py <プロジェクト> <名前> --interval 2",
  description: "<名前> の回答待ち",
  timeout_ms: 1800000,     # 30 分
  persistent: false
)
```

- 設問 1 件に回答が入るたびに 1 行届く。全問揃うと `[完了]` で終わる。
- **届いた回答に沿ってそのまま続きを実行する。** 全問揃うのを待つ必要はない。
- 30 分で切れたら、待ち受けが終わったことと未回答が残っていることをユーザーに伝える。放置しない。
- 完了へ移したレポートを見るときは `--done` を付ける。

**自動で実行してよい範囲**

- 回答が指示になっているもの（方針の選択、修正の可否、対応する / しない）は、そのまま実行してよい。
- ただし次は回答があっても**もう一度確認を取る**：本番への反映、データの削除・移行、外部への送信、コミット・プッシュ。
- 回答が「差し戻す」「補足だけで選択なし」のときは実行せず、内容を読んでから判断する。

**限界（ユーザーへ伝えること）**

- 待ち受けは**この会話が動いている間だけ**。閉じると止まる。閉じる前に待ち受け中のレポートがあれば伝える。
- 回答は後から入れても消えない。次のセッションの開始時に `.answers.json` を読めば拾える。

## 回答の取得方法（AI 側）

ユーザーがページで回答すると、同じ場所の `<名前>.answers.json` に保存される。

```bash
cat <report-hub>/reports/<プロジェクト>/<名前>.answers.json
curl -s http://localhost:5180/api/answers/<プロジェクト>/<名前>
curl -s http://localhost:5180/api/answers/<プロジェクト>/done/<名前>   # 完了へ移したもの
```

- ファイルが無い＝**まだ一件も回答されていない**。設問より回答が少なければ未回答が残っている。
- 回答が必要な作業は、**回答を読んでから**進める。勝手に既定値で進めない。

## レポートの状態 ＝ 置き場所で表す（進行中 / 完了）

状態は置き場所で決まる。ファイルの中に状態を書かない（二重管理になるため）。

| 状態 | 置き場所 | 意味 |
| :--- | :--- | :--- |
| 進行中 | `reports/<プロジェクト>/` | 回答待ち、または回答を受けて作業中 |
| 完了 | `reports/<プロジェクト>/done/` | 片が付いたもの。一覧では「完了 n 件」に畳まれる |

**完了へ移す条件**（すべて満たしたとき）

1. そのレポートの確認事項に回答が揃っている（未回答 0）。
2. 実施結果なら、完了確認の回答が「完了でよい」になっている。
3. 画面に触る変更なら、**実画面で開いて確認してある**。

```bash
cd <report-hub>/reports/<プロジェクト>
mkdir -p done
mv <名前>.html <名前>.answers.json done/   # HTML と回答は対で移す
mv done/<名前>.* .                          # 差し戻されたら戻す
```

**勝手に完了へ移さない。** 条件を満たしたうえで、ユーザーの確認を得てから移す。

## 画面に触る変更は、実画面で確認するまで完了としない

API やファイルの検証だけで済ませない。ブラウザで開けば即分かる不具合を、そこを見ないまま「確認した」と書かない。
確認できない事情がある（拡張が繋がらない等）なら、**レポートの残課題に明記してユーザーへ確認を依頼する**。黙って完了にしない。
開いて確かめたなら、**その現物を実施結果に貼る**（下記「実施結果には画面と動画を貼る」）。文章だけで済ませない。

## 1 レポート ＝ 1 回の問いかけ

回答が返ってきて、それを受けて次の判断を聞くときは、新しいレポートを起こす。前のレポートへ設問を足していかない。

- 足し続けると、決着済みの話と未決の話が同じページに混ざり、どこを見て何に答えればよいのか分からなくなる。
- 新しいレポートには、前回までに決まったことを 3〜5 行の要約と前のレポートの URL だけで示す。本文・表・設問を再掲しない。
- 前のレポートは、回答が揃っていれば完了へ移す（移してよいかはユーザーへ確認する）。
- 未回答が残っている設問を新しいレポートへ移すときは、`data-qa-id` ごと持っていく（過去の回答と結び付けるため）。移した側の元の設問は消す。
- 1 ページに載せる設問は、多くても 5〜6 問までを目安にする。それを超えるなら問いかけを分ける。

## チャットの返答は、最後の行に URL を置く

レポートを出した（新規・更新どちらも）ときの返答は、必ず最後の行にそのレポートの URL を書いて終える。

- 冒頭や本文の途中に URL を混ぜず、末尾に単独で置く。ユーザーが返答の一番下を見れば必ず開ける状態にする。
- 本文で先に結論を短く書き、最後に URL。順番を入れ替えない。
- 1 回の返答で触れたレポートが複数あるときは、末尾にまとめて並べる。
- 更新（上書き）のときも URL は同じなので、省かずに毎回書く。

## 修正内容の書き方 ＝ 画面・機能の単位

ファイル名・行番号の羅列にしない。**読む人が触る単位**（画面・機能・運用）で、いまどうなっていて、それをどう変えたかを書く。
表にせず、対象 1 件を 1 枚のカード（`div.change`）にする。

```html
<div class="change">
  <h3>レポート一覧</h3>
  <span class="tag">いま</span>
  <span class="from">レポート名と更新時刻が並ぶだけで、未回答があるか開くまで分からない</span>
  <span class="arrow" aria-hidden="true">↓</span>
  <span class="tag to">こうした</span>
  <span class="to">答え待ちを上に集めた 1 本のリストにし、未回答と経過日数を各行に出す</span>
</div>
```

- ラベルは、これから直す計画なら「いま」「こう直す」、済んだ話なら「いま」「こうした」。
- カード 1 枚 1 事象。実装の話（関数名・行番号・差分）は書かない。
- 直した不具合は「何が起きていたか → 原因 → どう直したか」を 1 行で。

## 時系列のあるものは表か mermaid の図にする

**操作の順序・状態が移り変わる話・何がいつ起きて何がどうなったか**は、文章で並べずに表か mermaid の図にする。

- 目安：分岐や合流が無く項目が並ぶだけなら**表**。順序に分岐・合流・戻りがあるなら**mermaid の図**。
- スライド様式では `<pre class="mermaid">` の中に記法を書く（class 名は固定。id は付けない）。`/assets/slide.js` が図のある枚を検出したときだけ `mermaid.min.js` を読み込んで描画する。
- 図で示すのは順序と分岐だけにし、中身の説明は図の外側の本文に書く。
- 図は 1 枚に収まる大きさにする。ノードは 5 つ程度までを目安にし、縦に伸びるなら横（`flowchart LR`）にする。
- 図を書いたら実際に開いて、1 枚に収まっているかを確かめる。
- **図は多用する。** 時系列に限らず、想定と実際の食い違い・依存の順番・枝分かれ・失敗時の分かれ道・構成など、文章だけでは組み立てにくい話には図を付ける。レビューの High には原則すべて付ける。
- 図は論点を説明している枚（`div.item` の中、設問より前）に置き、直前に「この図が何を示すか」を 1 行書く。図には本文が書いていることだけを描く。
- 折り返しは `&lt;br&gt;` と書く。`<pre>` の中の生の `<br>` はブラウザが要素として読み、mermaid に渡る前に消える（2 行がくっつく）。
- 2 つの流れを並べて比べるときは、外側を `flowchart TB`、各 `subgraph` の中を `direction LR` にし、`S1 ~~~ S2` で上下に積む。

```html
<pre class="mermaid">
sequenceDiagram
  participant U as 申請者
  participant A as 承認者
  U->>A: 申請を提出
  A-->>U: 差し戻し
  U->>A: 修正して再提出
  A-->>U: 承認
</pre>
```

## 番号・ID だけで書かない

**読む人が中身を知らない番号（マイグレーション番号・行番号・内部 ID など）は、何のことかを添えて書く。** 番号だけ書いても、読む人は中身を思い出せない。

- 形は「何をするものか（番号）」。例：「列を足す段（0005）は、値を必須にする段（0004）の後にしか流せない」。
- 同じ番号が何度も出るなら、前の方の枚に「番号と中身」の早見表を 1 つ置く。見出し・要点・図のラベルにも中身を添える。

## 手順書・テスト手順の書き方 ＝ 1 手順 1 操作

**手順書とテスト手順は、1 手順に操作を 1 つだけ書く。** まとめて書くと、途中で失敗したときにどこまで進んだのか分からなくなり、人に渡しても同じようには再現できない。

- **「〜して、〜する」で繋がっていたら分ける。** 「開いて設定を入れて保存する」は 3 手順。1 手順は、人が手を 1 回動かして終わる大きさにする。
- **手順の頭は動詞にする**（開く／押す／入れる／貼る／実行する／確かめる）。「〜の設定」のような名詞止めにしない。
- **どこでやるかを手順ごとに書く。** 画面名・ファイルのパス・シェルのどれか。読む人が手順の途中で「今どこを見ているのか」を見失わないため。
- **1 手順に 1 コマンド。** 複数行のコマンド塊を 1 手順に押し込まない。まとめて貼らせたいものは手順ではなく、ファイルの中身として別に置く。
- **その手順が済んだと分かる目印を 1 行付ける。** 出る画面・出る文字・できるファイル。目印を書けない手順は、確かめようがないので手順として成立していない。書き直す。
- **誰がやるかを分ける。** 人がやる操作と、AI・エージェントにやらせる操作を同じ番号列に混ぜない。段（章）ごとに分けるか、手順ごとに主体を書く。
- **失敗時の対処は手順に混ぜない。** その手順の直下に「うまくいかないとき」を 1 行で添える。分岐を手順の本文に埋めると、通常の道筋が読めなくなる。
- **前提の確認も手順にする。** 「プランに入っていること」は、確かめる操作（どこを開いて何を見るか）に開いて書く。

HTML では `<ol class="steps">` を使い、1 手順を `<li>` 1 つにする。

```html
<ol class="steps">
  <li>
    <span class="where">ブラウザ</span>
    <p class="do"><code>cursor.com/agents</code> を開く</p>
    <p class="ok">連携済みリポジトリの一覧が出る</p>
  </li>
  <li>
    <span class="where">ブラウザ</span>
    <p class="do">右上の <strong>Set up environment</strong> を押す</p>
    <p class="ok">セットアップの画面に切り替わる</p>
    <p class="ng">ボタンが無いときは、リポジトリの連携がまだ済んでいない</p>
  </li>
</ol>
```

- `span.where` … どこでやるか（画面名・パス・`シェル` など）。
- `p.do` … 操作 1 つ。
- `p.ok` … 済んだと分かる目印。**必ず書く。**
- `p.ng` … うまくいかないときの対処。要るときだけ。
- 番号は CSS が振る。手順の中に番号を書かない（順番を入れ替えたときに狂う）。

スライド様式では、**1 枚に 5 手順まで**。超えるなら段を割る。テスト手順も同じ形で書き、`p.ok` が期待結果にあたる。

## 実施結果には画面と動画を貼る

**画面に触る変更の実施結果には、`<h2>画面</h2>` の節を必ず入れる。** 文章だけでは、直した画面が実際どう見えるかが読む側に伝わらない。

- **直した画面ごとにスクリーンショットを 1 枚**、`<figure class="shot">` に `<img>` と 1 行の `<figcaption>` で置く。
- **操作の流れも短い動画（webm）で 1 本**貼る。`<video src="..." controls muted playsinline>` で置く。
- **横に 2 枚並べない。** 1 枚が小さくなって見づらい。見比べさせたいとき（直す前と後・狭い画面と広い画面）も `<div class="shots">` に `figure.shot` を 2 つ入れて**上下に**並べる。
- 説明は「**何の画面の、どこを見てほしいか**」を 1 行だけ。長い話は修正内容の側へ書く。

置き場所と参照の仕方：

- 置き場所：`<report-hub>/reports/<プロジェクト>/media/<日付>_<レポート名>-<何の画面か>.png`（動画は `.webm`）。
- レポートからは **`/r/<プロジェクト>/media/<ファイル>` の絶対パス**で参照する。完了へ移してもリンクが切れない。
- 使える拡張子は `png` / `jpg` / `gif` / `svg` / `webm` / `mp4`。ファイル名に使えるのは半角英数字・`.`・`_`・`-` のみ。

撮り方（Playwright がある場合）：

- スクリーンショットは `page.screenshot({ path })`。**画面の文字が出ないときはコンテナに日本語フォントが無い**ので入れる（Alpine なら `apk add font-noto-cjk`）。
- 動画は `test.use({ video: { mode: 'on', size: { width, height } } })`。**初回は `npx playwright install ffmpeg` が要る**（無いと録画時にエラーになる）。録れた `video.webm` は `test-results/` の下に出る。
- 撮るために作った使い捨てのテストは、**撮り終えたら消す**（リポジトリに残さない）。

## 確かめたことの書き方 ＝ 観点だけ

`<h2>確かめた観点</h2>` に `<ul class="aspects">` で**何を見たかだけ**を箇条書きにする。
結果の数字・手順・コマンド・テスト出力は書かない。別のエージェントにレビューを出したなら、それも観点の 1 つとして入れる。

## セッション開始時のルール

- 実施中の作業に計画レポートがあれば、対応内容・修正内容・懸念点と `.answers.json` の回答を確認する。
- `http://localhost:5180/` を見て、未回答が残っているレポートがないか確認する。
- 上記をもとに本日の作業内容をユーザーへ報告してから着手する。

## セッション終了時のルール

- 対応内容・修正内容・懸念点を計画レポートに記録（更新）する。
- 実施結果（実施した内容・結果・確認事項）を HTML レポートにまとめる。
- 完了条件を満たしたレポートがあれば、`done/` へ移してよいかをユーザーへ確認する。

## 計画レポートを出した後の運用ルール

- 計画レポートを作成・更新したら、その時点で一旦作業を止める。
- 着手可否の回答が入るまで実装・編集へ進まない。
- **回答は明示の指示として扱う。** 着手可否に「進める」「採用する」が入ったら、そのまま次の作業を始めてよい。
- 「差し戻す」「見送る」「選択なしで補足だけ」のときは進めず、内容を読んでから判断する。
- 戻せない操作（本番反映・データ削除・外部への送信・コミット）は、回答があっても実行前にもう一度確認する。

## 止まらずに進める

**入力が要らないステップは止まらずに続ける。** 途中で区切って「次へ進んでよいか」を聞かない。

- **状況報告は、次のアクションと同じメッセージに書く。** 報告だけのメッセージを単独で出さない。
  何をしたかを書いたら、同じメッセージの中でそのまま次の手を実行する。
- **止まって確認するのは次のときだけ。**
  1. ユーザーなしでは進められないとき（方針の選択・判断の材料が手元に無い・承認が要件になっている）。
  2. 破壊的な操作の前（データの削除、force-push、作業中のリポジトリ外への変更）。
- 上の 2 つに当たらないなら、確認せずに進める。確認の要否に迷ったら、進めたうえで
  何をしたかを報告し、戻せる形にしておく。
- コミット・プッシュ・本番反映・外部への送信は 2. に当たるので、従来どおり確認を取る。
  計画レポートの着手可否・`done/` へ移してよいかの確認は 1. に当たるので、こちらも従来どおり。
